# Рекомендации по устранению выявленных ошибок

В документе описаны проблемы, выявленные в ходе разработки и эксплуатации
`book-service`, и рекомендации по их устранению. Уже исправленные проблемы
в список не включены.

---

## 1. Отсутствие единой обработки ошибок на фронтенде

**Проблема.** Многие запросы к API выполняются без проверки статуса ответа.
Если сервер вернёт ошибку, попытка разобрать ответ как JSON приведёт к
исключению, и пользователь увидит пустой экран вместо понятного сообщения.

**Рекомендации.**

- Ввести единый вспомогательный модуль для работы с API, который проверяет
  статус ответа, единообразно извлекает тело ошибки и выбрасывает понятное
  исключение.
- Использовать этот модуль во всех компонентах вместо прямых вызовов `fetch`.
- Оборачивать вызовы в `try/catch` и показывать пользователю читаемое
  сообщение (баннер, всплывающее уведомление).
- Логировать полную информацию об ошибке в консоль для отладки.

---

## 2. Отсутствие глобального обработчика ошибок на сервере

**Проблема.** Каждый обработчик API ловит исключения самостоятельно.
Легко забыть `try/catch`, и тогда клиент получит неинформативный ответ
без тела.

**Рекомендации.**

- Ввести обёртку для обработчиков, которая централизованно ловит исключения
  и возвращает ответ в едином формате.
- Привести все эндпоинты к единому формату ошибок вида
  `{ error: string, code?: string }` — это упростит разбор на клиенте.
- Логировать все серверные ошибки с трассировкой стека.

---

## 3. Неполная валидация входных данных

**Проблема.** Не все эндпоинты проверяют входные данные. Некорректные
значения (например, несуществующий период аренды или нечисловой
идентификатор) приводят к ошибкам в рантайме вместо понятного ответа
клиенту.

**Рекомендации.**

- Добавить схемы валидации на каждый POST/PATCH-эндпоинт.
- Проверять параметры URL (например, идентификатор) на числовой формат
  до обращения к базе.
- Возвращать `400 Bad Request` с описанием проблемы, если данные
  не прошли валидацию.

---

## 4. Отсутствие проверки существования связанных сущностей

**Проблема.** При создании книги с несуществующей категорией или автором
база данных возвращает ошибку ограничения внешнего ключа. Пользователь
видит техническое сообщение вместо понятного объяснения.

**Рекомендации.**

- Перед созданием или обновлением записи проверять существование всех
  связанных сущностей.
- Возвращать `400 Bad Request` с указанием, какая именно связь
  некорректна.
- Либо перехватывать ошибку внешнего ключа и преобразовывать её
  в понятное сообщение.

---

## 5. Возможные гонки при одновременной аренде

**Проблема.** Если два пользователя одновременно арендуют одну и ту же
книгу, транзакция защищает от части проблем, но без явной блокировки
строки возможен сценарий, когда оба запроса прочитают статус
«доступна» и оба его обновят.

**Рекомендации.**

- Использовать пессимистичную блокировку строки при чтении книги
  внутри транзакции.
- Либо ввести уникальный индекс, запрещающий более одной активной
  аренды на одну книгу, и обрабатывать конфликт как `409 Conflict`.
- Добавить миграцию с таким индексом до выхода в продакшен.

---

## 6. Отсутствие фоновых задач для напоминаний и автовозврата

**Проблема.** По требованиям задания необходимо автоматически напоминать
пользователям об окончании аренды. Сейчас это не реализовано.

**Рекомендации.**

- Добавить планировщик задач, который периодически проверяет состояние
  аренд.
- Одна задача — автовозврат просроченных аренд: перевод аренды
  в статус «просрочена», возврат книги в статус «доступна», создание
  уведомления пользователю.
- Вторая задача — напоминание за сутки до окончания аренды. Важно
  проверять, что уведомление ещё не отправлялось, чтобы избежать
  дубликатов.
- Запускать планировщик при старте приложения.

---

## 7. Отсутствие автоматических тестов

**Проблема.** Логика аренды, покупки и регистрации не покрыта тестами.
Любая правка может незаметно сломать поведение.

**Рекомендации.**

- Внедрить тестовый фреймворк и писать тесты на критичные сценарии:
    - регистрация с занятым email;
    - аренда недоступной книги;
    - аренда несуществующей книги;
    - покупка уже проданной книги;
    - доступ к административным маршрутам под обычным пользователем.
- Использовать отдельную тестовую базу данных, которая пересоздаётся
  перед каждым запуском.

---

## 8. Отсутствие ограничения частоты запросов

**Проблема.** Эндпоинты регистрации и входа открыты для перебора паролей
и массового создания пользователей.

**Рекомендации.**

- Ввести ограничение частоты запросов для критичных эндпоинтов:
  регистрация, вход.
- При превышении лимита возвращать `429 Too Many Requests`
  с заголовком `Retry-After`.
- Для продакшена использовать внешнее хранилище счётчиков
  (например, Redis), для разработки достаточно in-memory.

---

## 9. Секреты в репозитории

**Проблема.** В файле окружения лежат реальные пароль базы данных
и секрет для подписи сессий. Случайный коммит приведёт к утечке.

**Рекомендации.**

- Убедиться, что файл окружения добавлен в `.gitignore` и никогда
  не попадает в репозиторий.
- Создать шаблон окружения с перечнем переменных без реальных значений
  и закоммитить его.
- В системах непрерывной интеграции и доставки использовать
  защищённые хранилища секретов.
- Для продакшена сгенерировать новые значения секретов, не
  переиспользовать dev-значения.

---

## 10. Отсутствие логирования и мониторинга

**Проблема.** Записи в консоль не сохраняются. При сбое в продакшене
невозможно установить причину.

**Рекомендации.**

- Подключить структурированный логгер.
- Логировать:
    - все серверные ошибки с трассировкой,
    - отказы в авторизации (для аудита безопасности),
    - медленные запросы,
    - ошибки базы данных с кодом.
- Для продакшена настроить отправку логов в централизованное хранилище
  и систему мониторинга ошибок.

---

## 11. Неполные состояния интерфейса

**Проблема.** На страницах с загрузкой данных пользователь не видит
индикатора загрузки, а при пустом списке — пояснения.

**Рекомендации.**

- Для каждой страницы с загрузкой предусмотреть три состояния:
  загрузка, ошибка, пустой результат.
- На время запроса блокировать кнопки, чтобы избежать повторных
  нажатий.
- Вместо простого текста «Загрузка» использовать скелетоны — это
  улучшает восприятие.

---

## 12. Отсутствие пагинации в каталоге

**Проблема.** Каталог возвращает все книги сразу. При росте базы
страница будет тормозить, а нагрузка на БД — расти.

**Рекомендации.**

- Добавить в API каталога постраничную выдачу с параметрами
  номера страницы и размера.
- Возвращать общее количество записей вместе со страницей, чтобы
  строить пагинацию на клиенте.
- На фронтенде добавить компонент пагинации или кнопку
  «Показать ещё».
- Учесть, что изменение формата ответа требует одновременного
  обновления фронтенда.

---

## 13. Нет возможности досрочного возврата книги пользователем

**Проблема.** Вернуть книгу может только администратор. Пользователь
не может сдать её раньше срока.

**Рекомендации.**

- Добавить эндпоинт для возврата книги пользователем, проверяющий,
  что аренда принадлежит текущему пользователю.
- Выполнять возврат в транзакции: изменить статус аренды, вернуть
  книге статус «доступна».
- При необходимости рассчитывать стоимость возврата пропорционально
  фактическому сроку аренды.
- На странице «Мои аренды» добавить кнопку возврата для активных
  аренд.

---

## 14. Удаление книги с активными арендами

**Проблема.** Администратор может удалить книгу, которая сейчас
арендована, оставив «висячую» аренду.

**Рекомендации.**

- Перед удалением проверять наличие активных аренд; если они есть —
  возвращать `409 Conflict` с пояснением.
- Предпочтительно использовать мягкое удаление: переводить книгу
  в статус «архив» вместо физического удаления. История аренд при
  этом сохраняется, а книга исчезает из каталога.

---

## 15. Отсутствие документации для развёртывания

**Проблема.** Без документации развернуть проект на другой машине
сложно, особенно с учётом особенностей используемой версии ORM
и драйверов.

**Рекомендации.**

- Создать файл README с разделами: стек, требования, установка,
  настройка окружения, миграции, запуск, тестовые учётные записи,
  типичные проблемы.
- Создать шаблон окружения с перечнем всех переменных.
- Добавить файл для запуска базы данных одной командой.
- Прописать в `package.json` скрипты для типовых действий:
  настройка базы, сброс, наполнение демо-данными.
