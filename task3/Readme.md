# Анализ выполненной задачи и рекомендации

## Часть 1. Анализ выполненной задачи

### 1. Архитектура проекта

Проект представляет собой микросервисную систему блога, состоящую из четырёх сервисов:

| Сервис         | Порт | Стек                             | Ответственность                                   |
| -------------- | ---- | -------------------------------- | ------------------------------------------------- |
| `auth-service` | 7001 | Express                          | Регистрация, логин, выдача JWT, refresh-токены    |
| `blog-service` | 7002 | Express + Sequelize + PostgreSQL | Посты, комментарии, медиа                         |
| `gateway`      | 7000 | Fastify + `@fastify/http-proxy`  | Единая точка входа, проксирование, аутентификация |
| `frontend`     | 5000 | React + Vite + MobX + Tailwind   | SPA                                               |

Слои `auth-service` и `blog-service` разделены: **routes → controllers → services → repositories → models**. Это позволяет независимо менять каждый уровень и тестировать изолированно.

Фронтенд построен по методологии **Feature-Sliced Design**: `app`, `pages`, `widgets`, `features`, `entities`, `shared`. Каждый слой знает только о нижних.

Gateway — единственная точка входа для браузера. Он проксирует `/auth` в `auth-service`, `/blog`, `/comments`, `/media` — в `blog-service`. Для защищённых маршрутов парсит JWT из `Authorization: Bearer` и прокидывает `x-user-id`, `x-user-email`, `x-user-role` в `blog-service`. CORS настроен только на gateway — внутренние сервисы к браузеру не обращаются.

### 2. Реализованный функционал

**auth-service:**

- регистрация и логин по email и паролю;
- выдача accessToken (короткоживущий) и refreshToken (долгоживущий, в httpOnly-куке);
- эндпоинт `/auth/refresh` для обновления accessToken;
- парсинг JWT на стороне gateway.

**blog-service:**

- CRUD постов с картинками (`multipart/form-data` через multer);
- видимость постов: гость видит только `isPublic: true, isHidden: false`, автор — все свои;
- пагинация, сортировка, фильтр по тегам через `Op.overlap`;
- комментарии с поддержкой вложенности (`parentId`) и сборкой дерева;
- заявки на доступ к приватным постам (`PostAccessRequest`);
- валидация через `express-validator`;
- отдача медиа через `express.static('/media')`.

**gateway:**

- проксирование `/auth`, `/blog`, `/comments`, `/media`;
- `optionalAuthenticateAndAttachUser` — парсит JWT и прокидывает `x-user-id` в blog-service.

**frontend:**

- список постов с пагинацией, фильтром по тегам, сортировкой;
- страница поста с картинками и деревом комментариев;
- форма создания и редактирования поста с загрузкой картинок;
- форма добавления комментария и ответов;
- удаление поста с подтверждением;
- запрос доступа к приватным постам;
- авторизация через MobX + Context, refresh accessToken.

### 3. Инфраструктурные и архитектурные вызовы

По мере развития проекта от локального запуска до продакшна встают задачи, выходящие за рамки кода приложения. Их нужно решать до того, как они станут блокерами.

#### 3.1. Хранение медиафайлов

Сейчас файлы лежат на локальном диске рядом с кодом `blog-service`. Это работает в разработке и на одном сервере, но создаёт проблемы при росте:

- **Горизонтальное масштабирование невозможно.** Если запустить несколько инстансов `blog-service`, файл, загруженный через один инстанс, не будет виден другим. Пользователь видит картинку через один балансировщик и не видит через другой.
- **Потеря данных при деплое.** При пересоздании контейнера или переустановке сервиса локальные файлы исчезают, если не примонтирован volume. В Docker/Kubernetes без volume это гарантированная потеря.
- **Нет CDN.** Все запросы за картинками идут на сервер приложения, нагружая его. Для блога с картинками это существенная часть трафика.
- **Нет резервного копирования из коробки.** Файлы нужно отдельно бэкапить, тогда как S3-хранилища делают это автоматически.
- **Проблемы с безопасностью.** Файлы лежат в файловой системе рядом с кодом. При ошибке в конфигурации `express.static` может отдать лишнее.

**Решение:** вынести медиа в объектное хранилище (S3, MinIO, Garage, SeaweedFS) или в облачный сервис (Yandex Object Storage, Selectel S3, AWS S3). Загрузка через presigned URL — фронт льёт файл напрямую в хранилище, минуя бэкенд. В БД хранятся полные URL или ключи объектов. CDN перед хранилищем для кэширования.

#### 3.2. Балансировка нагрузки

Один сервер не выдержит роста. Появляется несколько инстансов каждого сервиса, и встают вопросы:

- **Stateless-сервисы.** Все сервисы должны быть без локального состояния: JWT в заголовке, refresh в куке, медиа — в S3, сессии — в Redis. Иначе балансировщик не сможет равномерно распределять запросы.
- **Sticky sessions.** Если что-то хранится в памяти инстанса (например, in-memory кэш), придётся либо использовать sticky sessions, либо вынести состояние во внешнее хранилище.
- **Healthchecks.** Балансировщик должен знать, какие инстансы живы. Каждый сервис отдаёт `/health`, gateway проверяет и не проксирует в мёртвые.
- **Service discovery.** При динамическом количестве инстансов (Kubernetes, Nomad) нужен механизм обнаружения — Consul, etcd, или DNS-based в Kubernetes.
- **Gateway как единая точка входа.** Сейчас gateway один. При росте — несколько инстансов за внешним балансировщиком (nginx, HAProxy, облачный LB).

**Решение:** все сервисы делать stateless, состояние выносить в Redis/БД/S3. Настроить healthchecks и service discovery. Gateway масштабировать горизонтально за внешним LB.

#### 3.3. Асинхронная обработка

Сейчас все операции синхронные: запрос → обработка → ответ. Это работает до определённого момента:

- **Тяжёлые операции блокируют ответ.** Ресайз картинок, генерация превью, отправка email, обработка видео — всё это секунды, и пользователь ждёт.
- **Нет ретраев.** Если внешний сервис недоступен (email, S3), операция просто падает.
- **Пиковые нагрузки.** При всплеске запросов сервис не справляется, потому что обрабатывает всё синхронно.

**Решение:** вынести тяжёлые операции в очередь (RabbitMQ, Kafka, BullMQ на Redis). Примеры:

- после загрузки картинки — задача на ресайз и генерацию превью;
- после создания поста — задача на индексацию для поиска;
- после регистрации — задача на отправку приветственного email;
- периодическая очистка «сиротских» файлов в S3.

Очередь даёт ретраи, гарантию доставки, разгрузку основного потока.

#### 3.4. Кэширование

С ростом нагрузки БД становится узким местом:

- **Тяжёлые запросы** (`findAndCountAll` по большой таблице) выполняются на каждый запрос списка постов.
- **Одни и те же данные** запрашиваются многократно (популярные посты, топ тегов).
- **Горячие страницы** создают одинаковую нагрузку на БД.

**Решение:** Redis для кэширования.

- Список постов с фильтрами — кэш на 1–5 минут, инвалидация при создании/удалении.
- Отдельные посты — кэш с инвалидацией по ID.
- Счётчики (комментарии, лайки) — кэш в Redis.
- Сессии и refresh-токены — Redis вместо localStorage/БД.

На фронте — TanStack Query с `staleTime` и `keepPreviousData`, чтобы не дёргать API на каждое действие.

#### 3.5. Поиск

`ILIKE '%query%'` по `title` и `content` работает на маленьких объёмах, но не масштабируется:

- **Полнотекстовый поиск** с ранжированием — Postgres `tsvector` или Elasticsearch.
- **Поиск по тегам** с фасетами (сколько постов на каждый тег) — отдельный индекс.
- **Морфология** — «коты» и «кот» должны находиться.
- **Опечатки** — fuzzy-поиск.

**Решение:** для начала — Postgres `tsvector` с GIN-индексом. При росте — Elasticsearch/Meilisearch/Typesense. Для тегов — материализованное представление с агрегацией.

#### 3.6. Мониторинг и observability

Без мониторинга невозможно понять, что происходит в продакшне:

- **Метрики** — количество запросов, latency (p50/p95/p99), ошибки, использование ресурсов. Prometheus + Grafana.
- **Логи** — structured logging через pino, агрегация в Loki/ELK. Каждый лог с `requestId`, `userId`, `service`.
- **Трассировка** — OpenTelemetry через все сервисы. Видно, где именно тормозит запрос: gateway, blog-service, БД.
- **Алерты** — при превышении latency, росте ошибок, недоступности сервиса. Alertmanager, Opsgenie.
- **Error tracking** — Sentry на фронте и бэке. Ловит ошибки в проде с контекстом.

Без этого дебаг в продакшне превращается в гадание.

#### 3.7. Безопасность

С ростом проекта растут и риски:

- **Rate limiting** — защита от брутфорса логина, спама комментариями, DoS. `@fastify/rate-limit` на gateway.
- **WAF** — защита от SQL-инъекций, XSS, ботов. Cloudflare, ModSecurity.
- **HTTPS везде** — TLS-терминация на балансировщике, HSTS.
- **CSP** — Content-Security-Policy для защиты от XSS.
- **Секреты** — Vault, AWS Secrets Manager, Kubernetes Secrets. Не в `.env` в репозитории.
- **Ротация токенов** — короткоживущие accessToken (15 минут), refresh с ротацией.
- **Аудит** — логирование всех действий пользователя (создание, удаление, доступ).
- **Валидация загружаемых файлов** — не только MIME, но и содержимое (magic bytes). Ресайз через sharp отсекает много атак.

#### 3.8. Резервное копирование и восстановление

- **БД** — ежедневные снапшоты + WAL для point-in-time recovery. Реплика для отказоустойчивости.
- **Медиа** — версионирование в S3, lifecycle-политики для старых версий.
- **Конфигурации** — в git, секреты — в Vault.
- **Тесты восстановления** — регулярно проверять, что из бэкапа реально можно восстановиться.

Без этого любая авария — потеря данных.

#### 3.9. CI/CD

Ручной деплой не масштабируется:

- **CI** — линт, типы, тесты, сборка на каждый PR. GitHub Actions, GitLab CI.
- **CD** — автоматический деплой в staging и prod. ArgoCD, Flux для Kubernetes, или простые скрипты.
- **Миграции БД** — отдельный шаг в деплое, с проверкой наката и отката.
- **Blue-green или canary** — деплой без простоя и с возможностью отката.
- **Smoke-тесты** — после деплоя автоматически проверять, что основные сценарии работают.

#### 3.10. Схема данных и эволюция

По мере роста меняется модель данных:

- **Денормализация** — счётчики комментариев в `posts`, чтобы не делать `COUNT(*)` на каждый запрос.
- **Материализованные представления** — для тяжёлых агрегатов (топ тегов, активные авторы).
- **Партиционирование** — большие таблицы (`posts`, `comments`) по дате.
- **Шардирование** — при экстремальном росте, по `authorId` или `postId`.
- **Read-реплики** — для тяжёлых читающих запросов.
- **Кэш на уровне БД** — `pgbouncer` для пула соединений.

#### 3.11. Локализация и интернационализация

Если проект выходит за пределы одной страны:

- **Мультиязычный контент** — посты на разных языках.
- **Локализация интерфейса** — i18n на фронте (`react-i18next`).
- **Таймзоны** — даты в UTC, отображение в локальной таймзоне.
- **Валюта и форматы** — если появится монетизация.

#### 3.12. Правовые и регуляторные аспекты

- **GDPR / 152-ФЗ** — хранение персональных данных, право на удаление, экспорт данных.
- **Модерация контента** — жалобы, блокировки, автоматические фильтры.
- **Возрастные ограничения** — если контент может быть неприемлемым.
- **Лицензии** — для медиа, кода, зависимостей.

### 4. Общая оценка выполненной работы

**Что сделано:** рабочий микросервисный блог с CRUD постов, комментариями, медиа, авторизацией и разграничением доступа. Чёткое разделение слоёв, FSD на фронте, единая точка входа через gateway.

**Что предстоит:** перевод медиа в объектное хранилище, балансировка, кэширование, асинхронная обработка, мониторинг, безопасность, CI/CD. Это инфраструктурные задачи, которые решаются по мере роста нагрузки и требований.

### Порядок действий для ближайшего развития

1. **Вынести медиа в S3/MinIO** — иначе при первом же деплое потеряются картинки.
2. **Настроить CI/CD** — автоматический деплой с тестами.
3. **Подключить Sentry и pino** — без этого дебаг в проде невозможен.
4. **Метрики Prometheus + Grafana** — понять, где узкие места.
5. **Healthchecks + балансировщик** — для горизонтального масштабирования.
6. **Redis для кэша и сессий** — когда БД начнёт упираться.
7. **Rate limiting и CSP** — до публичного запуска.
8. **Бэкапы БД и S3** — с первого дня.
9. **Очередь для тяжёлых операций** — когда появятся ресайз, email, индексация.
10. **Полнотекстовый поиск** — когда `ILIKE` начнёт тормозить.
